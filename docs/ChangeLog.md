
# 1.19.0
- **Add `ctxt.cores` / `$DFM_CORES`** -- how many CPU cores the running task may use. A task that shells out to something with a parallelism flag passes this down (`make -j $DFM_CORES`) instead of asking the machine how many CPUs it has: under a batch scheduler the machine's answer is the *node's* core count rather than this job's allocation, and using it oversubscribes the node. Resolution order is `DFM_CORES` (explicit override, and the channel a runner backend uses to state an allocation), then the **actual** batch allocation (`LSB_DJOB_NUMPROC`, `LSB_MCPU_HOSTS`, `SLURM_CPUS_PER_TASK`, `NSLOTS`) -- the allocation and not the request, since they can differ and only one is true -- then the runner's `-j` budget, then the CPU count.
- Fix: the Verilator image build invoked `make ... -j` with **no number**, which to GNU make means *unlimited*. Several images building at once therefore spawned unbounded `g++`, and on a large UVM testbench the OOM killer took `cc1plus` — a build failure that looked like a compile error. It now passes `-j ${ctxt.cores}`.
- Known gap: locally the `-j` budget is not divided among concurrently running tasks, so several heavy builds can still oversubscribe. Weighted admission (a task consuming `cores` of the budget, the same number `std.ResourceTag` already sends to `bsub -n`) is the fix; until then `DFM_CORES` or a smaller `-j` is the lever.
- **Add `requires:` -- a task's contract, checked at graph build.** A task lists the checks it must satisfy (`requires: [std.check.Implemented]`), in exactly the shape `tags:` already uses: a list of parameterized type instances. A check is an ordinary type carrying a `check: module:function` callable, so declaring one costs no new machinery -- `types:` for the parameters, the tag instantiation path for the per-use overrides, `dfm show types` for the docs.
- This closes the one archetype property DFM did not have: **a declared-but-unfilled slot is now diagnosed**. A root task a base project declares and a leaf never implements previously *ran and reported success* -- the worst outcome for a shared project interface, because it makes `dfm run <verb>` trustworthy in one project and meaningless in the next. It now fails with a diagnostic that names where the requirement came from and what to type.
- Ships `std.check.Implemented` (the task must have a `run:`, a body, or a need) and `std.check.Needs` (`min`/`max`/`named`, plus `produces:` -- a *pattern* that must be reachable **transitively** through the task's needs, with the same subset-match rule a `consumes:` pattern uses, so `{type: hdlsim.SimRun}` and `{type: hdlsim.SimImg, build: prof}` are both expressible against one artifact type rather than a type per variant).
- **The static contract is a coarse gate, not a proof, and that is the design.** It checks what tasks *declare*, at graph build, before anything runs -- which is where the value is: cheap, early, and a statement of what kind of input a task expects, legible to a reader or a tool assembling a flow. It does not replace a task checking its actual inputs. A profile analyzer requires a `hdlsim.SimRun`; whether that run emitted profile data is a property of the data, known only after the run, and the task checks that itself and fails with a message about the data. Attributes are worth naming statically only where the producer genuinely declares them up front.
- Checks run after override resolution (so a leaf's `override:` is what satisfies a base's requirement -- this is the whole mechanism), after `iff:` (a node that does not exist is not checked), and after elaboration (so they see the wired graph, not the declaration). Requirements **accumulate** along the `uses:` chain, nearest-wins per `(check type, id)`; `severity: off` is the documented way for a project to decline an inherited requirement, leaving an auditable record in the flow file rather than a silent pass.
- The invoked root's checks are deferred until `--needs` has been wired, since its need-set is not final before then. A node built only to source a `uses:` implementation is not checked -- nobody asked for it, and its contract belongs to whatever derives from it.
- **Graph-build diagnostics now reach the user and gate the run.** The builder's marker channel defaulted to a no-op and was never wired by `dfm run`, so anything reported during graph build was recorded and discarded. A contract that reports and then runs anyway is worse than no contract.
- Fix: a type declared in a **fragment** was unreachable from another package. Type-name resolution split on the LAST dot and looked for a package by that prefix, so `std.check.Implemented` sent it looking for a package called `std.check`. It now tries each split point, longest prefix first.
- **Package variables can be exposed as command-line flags too** -- same declaration (`cli: true` on the variable), and it means a project-wide knob rather than one task's argument, so it applies to whatever task is being run: `dfm run tests --build dbg`. Collected along the package `uses:` chain, so a **base project can define a command-line interface its leaves inherit** -- a family of projects gets the same flags without restating them. `dfm run <task> --help` lists them under **Project options**, since from the command line they are indistinguishable from the task's own, and an unrecognized flag names them.
- A package flag takes effect **during the load**, not after it. A package variable is read while the flow loads (a `select:` family's axes, an `iff:`), so binding it afterwards would make `--build cov` and `-D build=cov` mean different things. Supplying one therefore reloads the project with the value folded in -- paid only when a package flag is actually used.
- If a task parameter and a package variable claim the same flag, the **task parameter wins** and a warning names both declarations; the package variable stays reachable as `-D <name>=<value>`. Neither site can see the other, so the rule is stated rather than resolved silently.
- **The CLI-facing views now show a parameter's value, not the expression that computes it.** A lazily-evaluated default is stored as its source text, so `dfm run <task> --help` printed `[default: ${{ build }}]` and `dfm show task` printed `= ${{ build }}` where the user wants `opt`. Both now resolve, and both reflect `-D`/`-P`, so what is shown is what the invocation would actually use. A select family's `default:` resolves too (`Cells (default: view=tlm, build=opt)`), and a cell's own parameters resolve against its axis bindings (`msg = built cov`, not `built ${{ this.build }}`). The `--usage --json` document carries the resolved value, since that is what a completion script or editor integration reads.
- Resolution for display is **not load-bearing**: `TaskGraphBuilder.resolveTaskParams` builds the parameter type only and constructs **no nodes**, so describing a task never builds -- or fails on -- that task's dependencies, and any failure degrades to showing the declared text rather than breaking the command.
- **Variant families are discoverable.** `dfm run` with no task lists the **family**, with its axes standing in for the cells (`sim-img - Simulation images [view: tlm,wb,rtl x build: opt,dbg]`) -- a 3x4 family would otherwise be twelve lines drowning everything else the project offers. `dfm show task <family>` is where the cells live: the axes, which cell the bare name denotes, and every cell name; `dfm show task <cell>` names its family and its bindings. Both are in `--json` as well as the rendered view, and completion offers cell names with no extra wiring, since a cell is an ordinary entry in the task namespace.
- **Add `dfm run <task> --needs <task>`** -- supply an input to the task being run from the command line, as if it appeared in that task's `needs:`. It is the same edge, so it resolves by the same (possibly partial) name and its data reaches the task the same way; a `select:` cell key works, which is what makes "analyze *the profiling build*" expressible. This is what lets a task shipped by a tool package consume a project's artifact without either project listing the other: `dfm run hdlsim.prof.Analyze --needs my-proj.sim-img.prof`. **Additive** (never replaces a declared dependency) and **root-only** (it cannot rewire the middle of a flow). Repeatable; an unresolvable name stops the run before anything executes. Rejected with an explanation under `DFM_SERVER_SOCKET`, where the protocol cannot carry it -- a silently unwired `--needs` would produce a run that looks fine and used the wrong input.
- Fix: a **deferred (per-cell) need was never wired into a compound body's `input`**. A compound consumes its dependencies through `input` (needs are gathered, then `input.needs` is extended from them), and a deferred need is resolved after that has already happened -- so the interior built without the very thing the cell asked for. Latent until now because it could only affect a matrix body that was a compound, and the idiom is a leaf; a `select:` body is naturally a compound. The same rule applies to `--needs` on a compound root.
- Fix: a **dotted name inside a fragment is now retried fragment-qualified**. A dot used to mean "already package-qualified", so a local reference like `needs: [sim-img.rtl.opt]` was never tried as `<fragment>.sim-img.rtl.opt` -- and failed with a "did you mean" hint naming the exact task it should have found. The retry runs only after the plain lookup fails, so no name that resolves today changes meaning.
- **Add `strategy.select` -- artifact variant families.** A cross product can mean two things, and only one of them was expressible. `matrix:` fans a task out: running it runs every cell, which is right for a regression suite (a suite *is* all of its cases). `select:` declares a **catalog**: each cell is a first-class task named `<family>.<key>`, so twelve simulation images (3 tops x 4 build variants) come from one body, and asking for one **does not build the other eleven**. This is deliberately not `iff:` gating -- `iff: false` still constructs a node and still builds its upstream.
- Cells are ordinary tasks in the package namespace, which is the whole design: `needs: [sim-img.rtl.cov]`, `dfm run sim-img.rtl.cov`, `dfm show task`, and tab completion all work with no per-consumer special-casing, and because the builder memoizes by name, **two consumers of one cell share one build** (a regression running six cases over three views compiles three images, not six). A cell's rundir is fixed by its name, not by which consumer happened to trigger construction, so a shared artifact does not move with graph traversal order.
- What the bare family name means is **declared, not guessed**: `default:` is a binding map (the family is an *alias* for one cell -- both spellings reach the same node), `all` (a gate over every cell), or `none` (only cells are addressable; naming the family is an error that lists them). A binding may name several values to gate a sub-family.
- The `default:` binding is an expression over the family's **own parameters**, which is what wires one project-wide knob to which artifact gets built: package variable -> task parameter -> `-D` -> `--flag` -> an explicit cell name, in that precedence order. This is what a `config:` could never express -- a configuration is global, so two artifacts in one run cannot differ; as an axis, "RTL image in debug, TLM image optimized" is just two cells.
- A body's `${{ this.<axis> }}` is bound per cell in parameters **and** in `needs:`, so `needs: ["flags-comp-${{ this.build }}"]` picks a different flag-holder per variant with no hand-written task per cell.
- **Command-line partial keys**: `dfm run sim-img.prof` names one axis and takes the rest from the default. A partial key in a `needs:` is a **load error** naming the full keys it could have meant -- a build file must not change meaning because a default moved, while a command line reasonably may. A key that could bind two axes, or one axis twice, is an error rather than a guess.
- A select family's **shape is fixed at load** (unlike a matrix, whose axes expand at graph build): an axis is a literal list or an expression over package variables, and may not depend on a `set:`/`let` rebind, since a family whose shape varied by instantiation site could not have stable cell names. An unresolvable axis is a marker naming the axis.
- `select:` composes with `std.TestRunner` selection from the opposite direction, without either knowing about the other: the runner prunes cases from the consumer side, and an unaddressed cell is never generated on the producer side. `dfm run tests --views rtl -D build=cov` compiles exactly one image out of six.
- **Add `std.TestInfo` -- the introspection companion to `std.TestRunner`.** A root `uses: std.TestInfo` and reports the inventory the runner selects over: the case names `--tests` accepts and the view names `--views` accepts, per suite and as a union. It **builds nothing** -- every declared need is dropped at graph build, so asking what tests exist never compiles a simulation image. The inventory is read off the runner named by `target:` (a bare name resolving in the info task's own package first), *not* off a duplicate `needs:` list, because a copy would drift the moment a suite was added; there is no `needs: [<task>.needs]` syntax, and this is the equivalent. Classification reuses `test_select.plan_need`, so what is reported and what selection accepts cannot disagree. `tests-info.json` is written to the rundir for scripted use; an unresolvable `target:` is an error rather than an empty inventory that reads as "this project has no tests". The report is **hierarchical**: a task name is a path, so suites are grouped under the scope they were declared in (`fw-wb-dma.uvm` written once, with `uvm-universal`/`uvm-hs-only` indented under it) rather than repeating the shared prefix on every row. A single-child, suite-less scope is joined onto its child (`p.uvm`, not `p` > `uvm`), and declaration order -- the order the flow file is written in -- is preserved.
- **Add `std.TestRunner` -- a built-in base task that turns a root into a project's test-execution command.** A root `uses: std.TestRunner`, wires the available cases and suites as `needs:`, and gets command-line **selection** (`--tests`, `--views`) plus an end-of-run **test report** (`--detail quiet|normal|full`). Selection prunes the need-set **at graph build**, so a deselected case is *never built* -- and neither is anything reachable only through it, which is why deselecting a DUT view also skips compiling that view's simulation image. This is deliberately not `iff:` gating: `iff: false` still constructs a stub node and still builds its upstream.
- Selection works at both granularities a project actually has: a **case** is a task carrying a `std.Test` tag (`tags: [{std.Test: {case: arb, view: rtl}}]`), kept or dropped whole; a **suite** is a matrix task whose cells carry a `name` field, rebuilt as a variant whose axis holds only the selected cells. Needs that are neither -- an image, a flags item, a helper -- are always kept, so selecting tests can never break the build.
- Selection is **strict by design**: naming a test or view that does not exist, or a selection matching nothing, is an error rather than a quietly green run that tested less than was asked for. Where a matrix axis is still an expression (`image: "${{ images }}"`) it is resolved so it can be validated; when it genuinely cannot be resolved, validation stays silent rather than reject a working flow.
- **An elaborator now sees final parameter values.** `ctxt.mkParams()` applies the full ladder (`default -> with:/kwargs -> -P -> -D -> --flag`) instead of returning declared defaults. Overrides were applied *after* the elaborator returned, so a task that elaborated based on a parameter silently decided from its default -- the same mistake load-time `${{ }}` expansion made, at a different phase. `ElabCtxt` also gains `expand()` (evaluate an expression in the elaboration context) and accepts a `Task` in `mkTaskNode` (build a locally-derived variant), both of which needs-pruning requires.
- Fix: `--flag a,b` on a list-typed task flag yielded `['a,b']` while `-D flag=a,b` yielded `['a','b']`. A list argument is collected with `action='append'`, which does not comma-split. Two spellings of the same override disagreeing is a trap, so the comma is now honored on both paths.
- Fix: `ElabCtxt.declaredNeeds` documented its return as `Need` objects; `Task.needs` holds `Task` objects. The documented `selectNeeds` contract now also states that it is invoked **once per `uses`-chain level** (so a filter must be idempotent) and that a pruned need is never built.
- **`run:` bodies are now expanded at graph build, once per node, instead of at load time once per task definition.** A `${{ }}` reference in a body previously rendered the *declared default*: load is the one moment when parameter values are guaranteed not to be final, so no override could reach it and every node built from a task shared one body. Now `-D`, `-P`, `set:`, and a task `--flag` all apply first, and `run: echo ${{ seed }}` agrees with `$DFM_PARAM_seed` and `dfm.params.json`. Expansion happens above the shell, so `pytask` bodies get it too.
- Fix a failure class that produced **no diagnostic at all**: a parameter default that referenced a package variable (`a: "${{ base }}-suffix"`) was stored lazily but spliced into the body eagerly, so the task died at execution with `/bin/bash: bad substitution` and no marker. Mixing eager and lazy evaluation of the same value is what caused it; both are now lazy.
- `${{ srcdir }}` in a body resolves to the directory of the file that **wrote** the body, which matters now that expansion is deferred: an inherited body carries its author's directory along the `uses:` chain rather than picking up the using task's.
- `${{ rundir }}` in a body remains a **run-phase** placeholder, resolved at execution as before.
- **Dangling `${{ }}` references are reported as load errors**, naming the task, the location (`run`, `parameter 'x'`), and a suggestion or the available names. Deferred evaluation removed the accidental check that eager substitution used to provide -- a typo no longer announces itself by failing to expand -- so validation is now its own pass over the *names* a description references, needing no values. `dfm validate` runs the same check as a phase alongside its existing undefined-task-reference check, in both text and `--json` output. Inherited parameters, package variables, package-qualified paths, `${{ x:-default }}`, and `this`/`matrix` roots are all accepted.
- **Removed `template: true`; added `abstract: true`.** The flag meant two unrelated things -- defer `run` expansion (now how every task works) and refuse direct invocation. The second keeps working under a name that means only that. A stale `template: true` is an unknown-field error, not a silent no-op. `template:` was added earlier in this same unreleased cycle and never shipped in a release.
- State and pin the parameter precedence ladder: `default -> with:/kwargs -> -P -> -D -> --flag`. In particular `-D` beats a programmatic `mkTaskNode(**kwargs)` value -- kwargs is how the description constructs a node, `-D` is the user overriding the description. This was previously true only as an artifact of statement order; both are now applied at a defined point, before the body is expanded.
- Performance: the expression parser and its parsed ASTs are **reused** instead of rebuilt per reference. Building a `ExprParser` costs ~221 us against ~2 us to parse, so evaluating a 3-reference string went from **~580 us to ~2 us (~270x)**. This is what makes per-node body expansion cheaper than the per-definition expansion it replaces, despite running more often.
- Add **first-class command-line arguments for task parameters** -- `dfm run run-tests --seed 42 --sim vcs` instead of only `-D name=value`. A parameter is exposed by its **own declaration**: `with: { seed: {type: int, value: 0, cli: true} }`. `cli: true` is the whole thing for the common case; the map form (`cli: {short: s}` / `{name: build}` / `{hidden: true}`) adds a short option, renames the flag, or keeps it out of help. Type, default, help text and accepted values are read off the parameter, so there is no second declaration to keep in sync -- and `values:` is the single set enforced on the flag, on `-D`, and on a `with:` override alike. `dfm run <task> --help` renders that task's arguments. Parsing is two-phase, because which flags a task accepts is only knowable once the flow has loaded: `run` takes the run options with `parse_known_args` and the leftovers go to a parser built from the task's exposed parameters. Bare task arguments are accepted; `--` is supported but not required.
- The parameter's declared **type shapes the flag**: `bool` becomes a switch, `list` becomes a repeatable (and comma-splitting) option, `int`/`float` are converted. `cli:` is inherited along `uses:` **per parameter**, so re-declaring a parameter to change its default keeps the base's flag; `cli: false` removes an inherited one.
- Task flags are validated at **load time**, as markers: two parameters claiming one flag, a bad short option, or a collision with a dfm option -- checked against the task's *effective* flag set, since inheritance alone can create a collision. The reserved-option list is derived from the argument parsers rather than hand-maintained, so adding a dfm option later turns a colliding task flag into a load error instead of silently stealing it.
- An earlier draft of this feature in this same unreleased cycle used a separate `cli:` **block** on the task (`cli: {args: [{name: seed, short: s, choices: [...]}]}`). That block is **removed**: it restated four things the parameter already declared (type, default, help, choices) to add two (`short`, `action`), and could drift from them. A stale block is an unknown-field error, not a silent no-op. Never shipped in a release.
- Task flags bind through the task-override map and therefore **beat `-D`** for the same parameter, and are keyed on the resolved full task name so a root's flag cannot leak into a nested task sharing its leaf name. Note the two mechanisms scope differently by design: `--seed` sets only the invoked root, while a bare `-D seed=42` still reaches every task that has a `seed` parameter.
- Extend `dfm complete` with **`--task <name>`**, listing that task's `cli:` flags for shell tab-completion.
- Add an **end-of-run task summary**, printed under every UI. A near-identical panel already existed, but it rendered from progress-listener state and so appeared only on a TTY with logging off -- piped and CI runs, the ones that most need a summary, got nothing. It is now built from the post-run node graph (`TaskNode.result`, populated on every path including remote execution), so it is backend- and UI-independent, and the progress listener delegates to it rather than keeping a second implementation. **Behavior change:** piped/CI `dfm run` now emits output it did not before; `--no-summary` opts out. Ordering is topological rather than observation order, so the panel's row order may differ slightly from previous releases.
- Add **`--summary-file PATH`** -- also write the summary to a file, format chosen by extension (`.md` → real markdown, anything else → plain text). Rendered at a fixed width with no ANSI, so the same run produces the same bytes locally and in CI. Independent of `--no-summary` ("silence the console, write the file"). A summary that returns nothing writes no file.
- Add the **`summary:` task capability** -- `summary: my_pkg.reports:regression` (a Python callable receiving a summary context and returning a rich renderable, a `str`, or `None`) or `summary: {builtin: task-summary}`. Resolved along the `uses:` chain, nearest declaration winning, whole-value replacement. The context exposes both a generic channel (per-task status/markers/timing) and the domain channel (the root's aggregated output), plus `task_summary()` so a custom summary can compose with the builtin instead of reimplementing it. Honored for the invoked root; a broken summary is reported and never changes the run's exit status.
- With both `summary:` and `--report DIR`, the summary is written into the bundle as `summary.md` and inlined into `report.md` -- so a project adopting `summary:` gets its roll-up in the GitHub job summary with no new Action inputs and no workflow edits.
- **`dfm run` now takes exactly one task.** `dfm run a b` is no longer accepted (build the targets in separate invocations, or wrap them in a compound root). The restriction is what makes the per-task front-end behavior (`cli:`, `summary:`, `--help`) well defined: with several roots there is no single task to take argument help, a `cli:` block, or a declared `summary:` from -- and, since bare task arguments are accepted, no way to tell a second task from a positional argument. A single-task `exec` subcommand was added earlier in this same unreleased cycle for that purpose and has been folded back into `run`; it never shipped in a release. The same restriction applies in `DFM_SERVER_SOCKET` client mode.
- Add **`dfm show task <name> --usage`** -- the CLI-shaped view of a task (how to invoke it, what arguments it takes, their types/defaults/docs) as opposed to the data-shaped detail view. `--json` combines with it and emits an `args` array for completion scripts and agents.
- Fix: parameters inherited through `uses:` are now **visible and overridable**. A task's `param_defs` holds only its own declarations, so a derived task previously listed none of its base's params in `dfm show task`, and `-D <task>.<inherited-param>=` failed with "Parameter not found" -- even though the node genuinely has the parameter. Both the qualified and bare `-D` forms now span the `uses:` chain, nearest declaration winning.
- Fix: a parameter's `doc:`/`desc:` were discarded at load, so every parameter description rendered blank. They are now carried onto the stored definition.
- Warn about **`-D` keys that bind nowhere**. A `-D` key is offered to package vars, task params by task name, and task params by bare name, and each consumer silently ignores what it does not recognize -- so a typo (`-D my_pkg.entrry.top=1`) previously ran as if nothing had been said. Keys that bind in two namespaces at once are also reported, with the qualified forms to use instead. Diagnostics only: binding semantics and exit status are unchanged.
- Add **`std.Publish` + `std.PubSet`** and a per-run **output-data directory**. Each `dfm run` has a designated output dir `rundir/out/<run-id>` (`<run-id>` is a zero-padded counter, or `--run-id <ID>` to pin it), with `rundir/out/latest` symlinked to the newest. `std.Publish` copies its consumed `std.FileSet`/`std.PubSet` files there under a path algebra (`dest` adds structure, signed `strip` rebases, `flatten` collapses to basename; the task `dest` composes as a base prefix in front of each PubSet's `dest`), writes a provenance manifest `.dfm-publish.json` (dest → publishing task, originating task, sha256, size), and detects conflicting overwrites (`on_conflict: error|warn|replace|skip`). `std.PubSet` binds a placement policy to a group of filesets so one `Publish` can place groups differently.
- Add **`dfm-out publish`** — the shell-task equivalent of `std.Publish`, copying files into `$DFM_OUT_DIR` with the same path algebra, provenance, and conflict handling. The runner exports `DFM_OUT_DIR`/`DFM_RUN_ID` to tasks.
- Materialize a **`rundir/bin`** with `dfm-out`/`dfm` shims that re-invoke the current interpreter and are placed on the task PATH, so shell tasks reach them without the console-script entry points being installed.
- Add the **`set:` block** for scoped subtree overrides: a list of assignment maps (rebind a scoped variable read via an ordinary `${{ pkg.var }}` reference) and/or scope items (`{uses?, path?, set: [...]}`) that narrow a rebind or force a parameter on matched descendants. Matchers: `uses:` (is-a over the node's `uses` chain) and `path:` (`*`/`**` globs). Precedence is *outer overrides inner*, with `-D` as the ceiling; `set:` overrides `with:`. Supersedes `let:`/`resolve()` (now deprecated but still working). hdlsim simulator selection is re-implemented on `set:` — the abstract tasks read `${{ hdlsim.sim }}`; select with `-D hdlsim.sim=<name>`, a subtree `set: [{ hdlsim.sim: <name> }]`, or a per-leg narrowed rebind.
- Fix `-D <pkg>.<name>=<value>` so it reaches ordinary `${{ pkg.var }}` reads (the override is now applied to the built package-params instance, not just the paramT default which pydantic v2 ignores at instantiation).
- Add **package maps** -- a generated `name -> flow file` manifest (`package-map:` key, `--package-map` flag, or `DV_FLOW_PACKAGE_MAP` env) that lets a project import dependencies by name without hard-coding paths. Maps register names lazily, so a dependency is parsed only when actually referenced. Multiple maps are supported (first-wins precedence).
- Import forms: import a package by `name` (located via map/registry), pin a name to an explicit file with `name`+`from`, and the `as:` alias is now honored -- an aliased import's tasks, types, and parameters resolve under the alias (e.g. `sim.SimImage`).
- Imports by name are loaded lazily: the dependency's flow file is parsed only when first referenced (unresolved names are still reported at load time). Building a task graph still materializes all reachable imports.
- Add `--report DIR` flag to `dfm run` -- writes a diagnostics bundle (per-task logs, markers, status as `report.json`/`report.md`/`markers.jsonl`) for publishing as a CI artifact. Assembled from each task's on-disk `exec_data.json`, so it is backend-agnostic (local, daemon, LSF). See the "Run Report Bundle" section of the command reference.
- `exec_data.json` now records each task's `markers` and `logfile` name (enables the backend-agnostic run report).
- Add Script ↔ Dataflow I/O contract for shell tasks: `DFM_*` env vars stage params/inputs/memento, and append-only files (`$DFM_OUTPUT`, `$DFM_ENV`, `$DFM_PATH`, `$DFM_MARKERS`, `$DFM_MEMENTO_OUT`) let scripts emit filesets, env, markers, and a memento downstream (GitHub-Actions-style). `TASK_SRCDIR`/`TASK_RUNDIR` retained as aliases.
- Add `dfm-out` helper CLI for emitting typed items/env/path/markers from shell tasks without hand-writing JSON
- ~~Add template tasks (`template: true`)~~ -- superseded within this same unreleased cycle: deferred `run` expansion is now unconditional and the abstract-task half became `abstract:` (see above). `template:` never shipped, so nothing to migrate.
- Add config-level task overrides (`overrides:` in configs) -- substitute arbitrary tasks when a config is active
- Add package-level task overrides (`overrides:` map on packages)
- Add `std.Null` no-op passthrough task for stubbing out tasks
- Add `--override TARGET=REPLACEMENT` CLI flag for ad-hoc task substitution
- Add `--runner` flag with auto-detect (daemon if running, else local)
