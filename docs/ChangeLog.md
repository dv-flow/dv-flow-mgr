
# 1.19.0
- **Add `std.TestInfo` -- the introspection companion to `std.TestRunner`.** A root `uses: std.TestInfo` and reports the inventory the runner selects over: the case names `--tests` accepts and the view names `--views` accepts, per suite and as a union. It **builds nothing** -- every declared need is dropped at graph build, so asking what tests exist never compiles a simulation image. The inventory is read off the runner named by `target:` (a bare name resolving in the info task's own package first), *not* off a duplicate `needs:` list, because a copy would drift the moment a suite was added; there is no `needs: [<task>.needs]` syntax, and this is the equivalent. Classification reuses `test_select.plan_need`, so what is reported and what selection accepts cannot disagree. `tests-info.json` is written to the rundir for scripted use; an unresolvable `target:` is an error rather than an empty inventory that reads as "this project has no tests". The report is **hierarchical**: a task name is a path, so suites are grouped under the scope they were declared in (`fw-wb-dma.uvm` written once, with `uvm-universal`/`uvm-hs-only` indented under it) rather than repeating the shared prefix on every row. A single-child, suite-less scope is joined onto its child (`p.uvm`, not `p` > `uvm`), and declaration order -- the order the flow file is written in -- is preserved.
- **Add `std.TestRunner` -- a built-in base task that turns a root into a project's test-execution command.** A root `uses: std.TestRunner`, wires the available cases and suites as `needs:`, and gets command-line **selection** (`--tests`, `--views`) plus an end-of-run **test report** (`--detail quiet|normal|full`). Selection prunes the need-set **at graph build**, so a deselected case is *never built* -- and neither is anything reachable only through it, which is why deselecting a DUT view also skips compiling that view's simulation image. This is deliberately not `iff:` gating: `iff: false` still constructs a stub node and still builds its upstream.
- Selection works at both granularities a project actually has: a **case** is a task carrying a `std.Test` tag (`tags: [{std.Test: {case: arb, view: rtl}}]`), kept or dropped whole; a **suite** is a matrix task whose cells carry a `name` field, rebuilt as a variant whose axis holds only the selected cells. Needs that are neither -- an image, a flags item, a helper -- are always kept, so selecting tests can never break the build.
- Selection is **strict by design**: naming a test or view that does not exist, or a selection matching nothing, is an error rather than a quietly green run that tested less than was asked for. Where a matrix axis is still an expression (`image: "${{ images }}"`) it is resolved so it can be validated; when it genuinely cannot be resolved, validation stays silent rather than reject a working flow.
- **An elaborator now sees final parameter values.** `ctxt.mkParams()` applies the full ladder (`default -> with:/kwargs -> -P -> -D -> --flag`) instead of returning declared defaults. Overrides were applied *after* the elaborator returned, so a task that elaborated based on a parameter silently decided from its default -- the same mistake load-time `${{ }}` expansion made, at a different phase. `ElabCtxt` also gains `expand()` (evaluate an expression in the elaboration context) and accepts a `Task` in `mkTaskNode` (build a locally-derived variant), both of which needs-pruning requires.
- Fix: `--flag a,b` on a list-typed `cli:` argument yielded `['a,b']` while `-D flag=a,b` yielded `['a','b']`. A list argument is collected with `action='append'`, which does not comma-split. Two spellings of the same override disagreeing is a trap, so the comma is now honored on both paths.
- Fix: `ElabCtxt.declaredNeeds` documented its return as `Need` objects; `Task.needs` holds `Task` objects. The documented `selectNeeds` contract now also states that it is invoked **once per `uses`-chain level** (so a filter must be idempotent) and that a pruned need is never built.
- **`run:` bodies are now expanded at graph build, once per node, instead of at load time once per task definition.** A `${{ }}` reference in a body previously rendered the *declared default*: load is the one moment when parameter values are guaranteed not to be final, so no override could reach it and every node built from a task shared one body. Now `-D`, `-P`, `set:`, and a `cli:` `--flag` all apply first, and `run: echo ${{ seed }}` agrees with `$DFM_PARAM_seed` and `dfm.params.json`. Expansion happens above the shell, so `pytask` bodies get it too.
- Fix a failure class that produced **no diagnostic at all**: a parameter default that referenced a package variable (`a: "${{ base }}-suffix"`) was stored lazily but spliced into the body eagerly, so the task died at execution with `/bin/bash: bad substitution` and no marker. Mixing eager and lazy evaluation of the same value is what caused it; both are now lazy.
- `${{ srcdir }}` in a body resolves to the directory of the file that **wrote** the body, which matters now that expansion is deferred: an inherited body carries its author's directory along the `uses:` chain rather than picking up the using task's.
- `${{ rundir }}` in a body remains a **run-phase** placeholder, resolved at execution as before.
- **Dangling `${{ }}` references are reported as load errors**, naming the task, the location (`run`, `parameter 'x'`), and a suggestion or the available names. Deferred evaluation removed the accidental check that eager substitution used to provide -- a typo no longer announces itself by failing to expand -- so validation is now its own pass over the *names* a description references, needing no values. `dfm validate` runs the same check as a phase alongside its existing undefined-task-reference check, in both text and `--json` output. Inherited parameters, package variables, package-qualified paths, `${{ x:-default }}`, and `this`/`matrix` roots are all accepted.
- **Removed `template: true`; added `abstract: true`.** The flag meant two unrelated things -- defer `run` expansion (now how every task works) and refuse direct invocation. The second keeps working under a name that means only that. A stale `template: true` is an unknown-field error, not a silent no-op. `template:` was added earlier in this same unreleased cycle and never shipped in a release.
- State and pin the parameter precedence ladder: `default -> with:/kwargs -> -P -> -D -> --flag`. In particular `-D` beats a programmatic `mkTaskNode(**kwargs)` value -- kwargs is how the description constructs a node, `-D` is the user overriding the description. This was previously true only as an artifact of statement order; both are now applied at a defined point, before the body is expanded.
- Performance: the expression parser and its parsed ASTs are **reused** instead of rebuilt per reference. Building a `ExprParser` costs ~221 us against ~2 us to parse, so evaluating a 3-reference string went from **~580 us to ~2 us (~270x)**. This is what makes per-node body expansion cheaper than the per-definition expansion it replaces, despite running more often.
- Add the **`cli:` task capability** -- a root task can declare first-class command-line arguments (`dfm run run-tests --seed 42 --sim vcs`) instead of only `-D name=value`. Every field but `name` defaults from the parameter the argument targets, so the common case is a one-liner. `dfm run <task> --help` renders that task's arguments. Parsing is two-phase, because which flags a task accepts is only knowable once the flow has loaded: `run` takes the run options with `parse_known_args` and the leftovers go to a parser built from the task's `cli:` block. Bare task arguments are accepted; `--` is supported but not required. `cli:` is inherited along `uses:`, nearest declaration winning, with whole-block replacement.
- `cli:` blocks are validated at **load time**, as markers: an argument naming a parameter the task does not have, a duplicate name or short option, or a collision with a dfm option. The reserved-option list is derived from the argument parsers rather than hand-maintained, so adding a dfm option later turns a colliding task flag into a load error instead of silently stealing it.
- Named arguments bind through the task-override map and therefore **beat `-D`** for the same parameter, and are keyed on the resolved full task name so a root's flag cannot leak into a nested task sharing its leaf name. Note the two mechanisms scope differently by design: `--seed` sets only the invoked root, while a bare `-D seed=42` still reaches every task that has a `seed` parameter.
- Extend `dfm complete` with **`--task <name>`**, listing that task's `cli:` flags for shell tab-completion.
- Add an **end-of-run task summary**, printed under every UI. A near-identical panel already existed, but it rendered from progress-listener state and so appeared only on a TTY with logging off -- piped and CI runs, the ones that most need a summary, got nothing. It is now built from the post-run node graph (`TaskNode.result`, populated on every path including remote execution), so it is backend- and UI-independent, and the progress listener delegates to it rather than keeping a second implementation. **Behavior change:** piped/CI `dfm run` now emits output it did not before; `--no-summary` opts out. Ordering is topological rather than observation order, so the panel's row order may differ slightly from previous releases.
- Add **`--summary-file PATH`** -- also write the summary to a file, format chosen by extension (`.md` → real markdown, anything else → plain text). Rendered at a fixed width with no ANSI, so the same run produces the same bytes locally and in CI. Independent of `--no-summary` ("silence the console, write the file"). A summary that returns nothing writes no file.
- Add the **`summary:` task capability** -- `summary: my_pkg.reports:regression` (a Python callable receiving a summary context and returning a rich renderable, a `str`, or `None`) or `summary: {builtin: task-summary}`. Resolved along the `uses:` chain, nearest declaration winning, whole-value replacement. The context exposes both a generic channel (per-task status/markers/timing) and the domain channel (the root's aggregated output), plus `task_summary()` so a custom summary can compose with the builtin instead of reimplementing it. Honored for the invoked root; a broken summary is reported and never changes the run's exit status.
- With both `summary:` and `--report DIR`, the summary is written into the bundle as `summary.md` and inlined into `report.md` -- so a project adopting `summary:` gets its roll-up in the GitHub job summary with no new Action inputs and no workflow edits.
- **`dfm run` now takes exactly one task.** `dfm run a b` is no longer accepted (build the targets in separate invocations, or wrap them in a compound root). The restriction is what makes the per-task front-end behavior (`cli:`, `summary:`, `--help`) well defined: with several roots there is no single task to take argument help, a `cli:` block, or a declared `summary:` from -- and, since bare task arguments are accepted, no way to tell a second task from a positional argument. A single-task `exec` subcommand was added earlier in this same unreleased cycle for that purpose and has been folded back into `run`; it never shipped in a release. The same restriction applies in `DFM_SERVER_SOCKET` client mode.
- Add **`dfm show task <name> --usage`** -- the CLI-shaped view of a task (how to invoke it, what arguments it takes, their types/defaults/docs) as opposed to the data-shaped detail view. `--json` combines with it and emits an `args` array for completion scripts and agents.
- Fix: parameters inherited through `uses:` are now **visible and overridable**. A task's `param_defs` holds only its own declarations, so a derived task previously listed none of its base's params in `dfm show task`, and `-D <task>.<inherited-param>=` failed with "Parameter not found" -- even though the node genuinely has the parameter. Both the qualified and bare `-D` forms now span the `uses:` chain, nearest declaration winning.
- Fix: a parameter's `doc:`/`desc:` were discarded at load, so every parameter description rendered blank. They are now carried onto the stored definition.
- Warn about **`-D` keys that bind nowhere**. A `-D` key is offered to package vars, task params by task name, and task params by bare name, and each consumer silently ignores what it does not recognize -- so a typo (`-D my_pkg.entrry.top=1`) previously ran as if nothing had been said. Keys that bind in two namespaces at once are also reported, with the qualified forms to use instead. Diagnostics only: binding semantics and exit status are unchanged.
- Add **`std.Publish` + `std.PubSet`** and a per-run **output-data directory**. Each `dfm run` has a designated output dir `rundir/out/<run-id>` (`<run-id>` is a zero-padded counter, or `--run-id <ID>` to pin it), with `rundir/out/latest` symlinked to the newest. `std.Publish` copies its consumed `std.FileSet`/`std.PubSet` files there under a path algebra (`dest` adds structure, signed `strip` rebases, `flatten` collapses to basename; the task `dest` composes as a base prefix in front of each PubSet's `dest`), writes a provenance manifest `.dfm-publish.json` (dest → publishing task, originating task, sha256, size), and detects conflicting overwrites (`on_conflict: error|warn|replace|skip`). `std.PubSet` binds a placement policy to a group of filesets so one `Publish` can place groups differently.
- Add **`dfm-out publish`** — the shell-task equivalent of `std.Publish`, copying files into `$DFM_OUT_DIR` with the same path algebra, provenance, and conflict handling. The runner exports `DFM_OUT_DIR`/`DFM_RUN_ID` to tasks.
- Materialize a **`rundir/bin`** with `dfm-out`/`dfm` shims that re-invoke the current interpreter and are placed on the task PATH, so shell tasks reach them without the console-script entry points being installed.
- Add the **`set:` block** for scoped subtree overrides: a list of assignment maps (rebind a scoped variable read via an ordinary `${{ pkg.var }}` reference) and/or scope items (`{uses?, path?, set: [...]}`) that narrow a rebind or force a parameter on matched descendants. Matchers: `uses:` (is-a over the node's `uses` chain) and `path:` (`*`/`**` globs). Precedence is *outer overrides inner*, with `-D` as the ceiling; `set:` overrides `with:`. Supersedes `let:`/`resolve()` (now deprecated but still working). hdlsim simulator selection is re-implemented on `set:` — the abstract tasks read `${{ hdlsim.sim }}`; select with `-D hdlsim.sim=<name>`, a subtree `set: [{ hdlsim.sim: <name> }]`, or a per-leg narrowed rebind.
- Fix `-D <pkg>.<name>=<value>` so it reaches ordinary `${{ pkg.var }}` reads (the override is now applied to the built package-params instance, not just the paramT default which pydantic v2 ignores at instantiation).
- Add **package maps** -- a generated `name -> flow file` manifest (`package-map:` key, `--package-map` flag, or `DV_FLOW_PACKAGE_MAP` env) that lets a project import dependencies by name without hard-coding paths. Maps register names lazily, so a dependency is parsed only when actually referenced. Multiple maps are supported (first-wins precedence).
- Import forms: import a package by `name` (located via map/registry), pin a name to an explicit file with `name`+`from`, and the `as:` alias is now honored -- an aliased import's tasks, types, and parameters resolve under the alias (e.g. `sim.SimImage`).
- Imports by name are loaded lazily: the dependency's flow file is parsed only when first referenced (unresolved names are still reported at load time). Building a task graph still materializes all reachable imports.
- Add `--report DIR` flag to `dfm run` -- writes a diagnostics bundle (per-task logs, markers, status as `report.json`/`report.md`/`markers.jsonl`) for publishing as a CI artifact. Assembled from each task's on-disk `exec_data.json`, so it is backend-agnostic (local, daemon, LSF). See the "Run Report Bundle" section of the command reference.
- `exec_data.json` now records each task's `markers` and `logfile` name (enables the backend-agnostic run report).
- Add Script ↔ Dataflow I/O contract for shell tasks: `DFM_*` env vars stage params/inputs/memento, and append-only files (`$DFM_OUTPUT`, `$DFM_ENV`, `$DFM_PATH`, `$DFM_MARKERS`, `$DFM_MEMENTO_OUT`) let scripts emit filesets, env, markers, and a memento downstream (GitHub-Actions-style). `TASK_SRCDIR`/`TASK_RUNDIR` retained as aliases.
- Add `dfm-out` helper CLI for emitting typed items/env/path/markers from shell tasks without hand-writing JSON
- ~~Add template tasks (`template: true`)~~ -- superseded within this same unreleased cycle: deferred `run` expansion is now unconditional and the abstract-task half became `abstract:` (see above). `template:` never shipped, so nothing to migrate.
- Add config-level task overrides (`overrides:` in configs) -- substitute arbitrary tasks when a config is active
- Add package-level task overrides (`overrides:` map on packages)
- Add `std.Null` no-op passthrough task for stubbing out tasks
- Add `--override TARGET=REPLACEMENT` CLI flag for ad-hoc task substitution
- Add `--runner` flag with auto-detect (daemon if running, else local)
